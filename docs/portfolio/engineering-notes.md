# 문제 해결 기록

## 1. 처방 입력값이 재조회에서도 같은 의미로 남도록

**확인한 문제:** 화면에서 실제 처방량을 입력했더라도 과거 상담·안내데스크 조회에서 표시 경로가 달라 값이 누락될 수 있었습니다. 원문에 있는 양을 실제 입력값처럼 표시하면 값의 의미도 바뀝니다.

**적용:** 원본 참고량, 실제 처방량, 실제 단위를 분리해서 저장·응답·표시하도록 점검했습니다. 공통 표시 함수와 검사를 추가하고, 값이 없는 경우에는 `미입력`을 표시하도록 구분했습니다. 화면 변경은 팀원 UI의 메뉴·배치·스타일과 분리했습니다.

**확인:** 저장 API·DB 값과 한의사·안내데스크 재조회 화면을 대조했습니다. 원본 `9 L`과 실제 `2.5 mL`를 구분한 검증 기록은 시연영상의 가상 `3 g / 2.5 g` 사례와 다른 기록입니다. 서로 다른 예시를 같은 데이터로 설명하지 않았습니다.

관련 위치: [`prescription_ingredients.py`](../../backend/prescription_ingredients.py), [`frontend/src/`](../../frontend/src/), [`처방 표시 테스트`](../../frontend/tests/prescriptionUtils.test.mjs)

## 2. 생성 설명의 대기 시간을 줄이면서 원문 검사 유지

**확인한 문제:** 여러 후보의 설명을 순차 생성·검토하면 사용자가 실제로 선택한 처방의 설명까지 오래 기다릴 수 있었습니다. 같은 내용을 다시 요청할 때도 같은 모델 처리가 반복됐습니다.

**적용:** 선택한 처방의 설명을 먼저 처리하고, 동일 조건에서 검증을 마친 완성 결과를 재사용했습니다. 취소·실패·미완성 응답과 성공 캐시를 구분했습니다. 속도를 줄이기 위해 원문 관계 검사나 생성 후 인용 검사·별도 검토 단계를 생략하지 않았습니다.

**확인:** 설명·캐시·취소·출력 중단 회귀 검사를 유지했습니다. 이후 Elice에서 CPU/GPU의 비교 조건을 고정하고 애플리케이션 완성 결과 캐시를 비운 상태로 시간을 측정했습니다. [측정 조건](verification.md)

관련 위치: [`ai/explanations.py`](../../backend/ai/explanations.py), [`ai/service.py`](../../backend/ai/service.py)

## 3. GPU가 보이는 상태와 모델이 실행되는 상태를 구분

**확인한 문제:** Elice 인스턴스에서 GPU를 조회할 수 있어도 실행 파일이 요구하는 glibc·libstdc++와 CUDA PTX 준비 조건이 맞지 않아 모델 실행이 실패했습니다.

**적용:** 검증한 실행 파일·모델 버전과 해시를 고정했습니다. 호환 라이브러리와 CUDA 호환 패키지는 전용 폴더에 추출하고, 해당 모델 프로세스에만 적용했습니다. 팀 서비스나 시스템 드라이버를 바꾸는 방식으로 처리하지 않았습니다.

**확인:** 33/33 레이어 GPU offload, 실제 생성·인용·검토 PASS, 서버 상태와 인증 없는 요청의 차단을 확인했습니다. CPU와 GPU 모두 같은 후보와 검증 함수를 사용했습니다.

관련 위치: [`Elice 실행·검증 기록`](../elice-gpu-benchmark.md), [`backend/scripts/`](../../backend/scripts/)

## 다음 개선에서 이어갈 부분

- 모델 초기 준비·첫 요청·반복 요청·동시 접속을 나눠 서비스 응답을 측정합니다.

이 항목은 현재 완료 실적으로 계산하지 않은 후속 과제입니다.
